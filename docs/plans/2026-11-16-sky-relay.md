# Sky Relay implementation plan

Ship the private-room flight relay already selected in the November 15 competitor follow-up. Current Krillion browser inspection again confirms Party, private codes, matchmaking and shared-fuse play. Implement an original flight relay in the existing sky interface.

Use the existing Cloudflare Worker and D1. A single room JSON snapshot plus an integer revision permits atomic compare-and-swap updates. Store frozen question sets with each room. Read deadlines on the server, settle elapsed turns before handling an action, and require the expected turn for submissions. Retrying a request cannot award points twice. Private seat tokens authenticate each player and stay in session storage, never shared URLs or public room state. Rooms expire after 24 hours. Existing Cloudflare bindings serve the feature.

Two to six players share five question stages. Each starts with three hearts. Correct, unused answers earn the existing rarity points and pass the turn. The shared 30-second clock keeps running with an eight-second minimum for the next player. A timeout costs one heart and starts the next question. Exhausting a question's answers also starts the next stage. One remaining pilot or five completed stages ends the game. Rank remaining hearts, then altitude, with equal results sharing rank. The host can start with at least two players. Joining is available in the lobby. Leaving transfers lobby hosting or removes that player's active turn. Reopening the tab resumes its seat while session storage is available.

1. Add the D1 room table and pure relay transitions in `src/relay.js`, reusing schedule, evaluate and answer localization. Add regression coverage for deduplication, timeouts, stale turns, leave/reconnect, authorization and final ranking.
2. Add room API persistence in `src/relay-api.ts` and route it from the existing Worker after same-origin and body validation. Verify compare-and-swap conflicts against local D1 with two independently authenticated seats.
3. Add `public/relay.js` and `public/relay.css` using the established typography, sky and balloon artwork. Add a home entry, invite code/link, lobby, pilot cards, accessible timer, localized answer form and final results. Poll only the active room, back off on failures and resume after visibility/network changes. Translate every new message into the existing ten languages.
4. Run the normal bank/site/type/unit checks, existing API integration, multiplayer integration, native and WeChat asset compatibility builds. Exercise two controlled clients through the normal UI and inspect mobile/RTL layout.
5. Apply the additive migration, push source, deploy, verify public entry and room API, then update the competitor execution record with actual delivered and outstanding capabilities.

The existing published native store binaries require their own later release. The multiplayer interface is packaged by the shared native build. The separate WeChat Canvas requires its own adaptation.
